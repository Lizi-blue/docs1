# Feature Specification: Agent 方向（演进、原理、DSH 平台与落地实践）

**Feature Branch**: `009-agent-domain`

**Created**: 2026-10-18

**Status**: Draft

**Repo Positioning**: 本仓是**文档与可行性研究仓**，用于研究可行性与沉淀学习文档。
本专题**不修改任何项目代码、不部署任何服务**；产出物只有 Markdown 页面与自包含图解，
结论要能直接指导集群后续的接入决策（自建还是用开源、代价是什么）。

**Input**: User description: 「新增一个 agent 方向，讲解 agent 由来从 llm 最基础的问答 到今天 agent 的进化与使用方式 整体演进，原理逻辑（agent 定义是什么，如何实现最小 agent，agent 如何协同？agent 如何并发？再基于 dsh 讲解，再讲解 dsh 的能力和局限，如果想实现：1. dsh 作为一个工作台 进行专项的复杂工作持续沟通交付 2. 但是像接入日历、ha 这种没必要固定死在 dsh 上，但是集群当前没有其他 agent，没有地方有 agent 管理日历 ha 等的上下文和记忆等（后续会接入一些其他的））尤其 agent 在 vibe coding 以及当前自维护 k3s 集群中能用 agent 做什么实现什么（基于当前 k3s 集群的 conf dsh opendesign 等其他未接入的开源项目）」

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从基础问答走到 agent 的主线（Priority: P1）

读者按一条主线读完演进：纯问答 → 上下文与提示 → 工具调用 → 规划与循环 → 多 agent 与平台化。
每段都能回答三件事：这一段解决了什么、它带来了什么新问题、agent 与「带工具的聊天」到底差在哪。

**Why this priority**: 没有主线，后面所有原理与平台内容都会变成零散名词。

**Independent Test**: 打开领域首页，按主线顺序读到末段；每段都有特征、能力、局限与追问链四项。

**Acceptance Scenarios**:

1. **Given** 新领域首页，**When** 浏览学习路径，**Then** 主线阶段按先后排列且可逐段进入。
2. **Given** 任一阶段页，**When** 阅读，**Then** 能看到「这一段解决了什么 / 带来了什么新问题」两问的答案。
3. **Given** 主线末段，**When** 阅读，**Then** 能说清 agent 与带工具聊天的差别判据。

### User Story 2 - 原理：定义、最小实现、协同、并发（Priority: P1）

读者能写出一个最小 agent（循环、工具、终止条件、失败处理），理解多 agent 的协作拓扑，理解并发与隔离。
读完能判断「这件事该用单 agent、多 agent，还是不该用 agent」。

**Why this priority**: 这是本方向的技术主干，也是面试区分度的来源。

**Independent Test**: 按页面示例在本地跑通最小 agent；对照三种协作拓扑与三类并发模型，各说出一个失败模式。

**Acceptance Scenarios**:

1. **Given** 最小 agent 讲，**When** 照示例执行，**Then** 在数分钟内得到预期输出，且示例含终止条件与失败处理。
2. **Given** 协同讲，**When** 阅读，**Then** 能区分主从、对等、流水线三类拓扑的适用与失败模式。
3. **Given** 并发讲，**When** 阅读，**Then** 能说清进程、线程、异步三种并发下的隔离与限额手段。
4. **Given** 任一场景，**When** 用页面判据评估，**Then** 能得出「该用/不该用 agent」的结论。

### User Story 3 - DSH 的能力与局限（Priority: P1）

读者能列出 DSH 能做什么、不能做什么，以及每条局限的规避方式；能判断哪些工作该交给 DSH、哪些不该。

**Why this priority**: 平台认知决定后面两条使用路线怎么选。

**Independent Test**: 对照能力表与局限表，各自抽查 3 条，核对是否能找到规避或替代做法。

**Acceptance Scenarios**:

1. **Given** 能力表，**When** 阅读，**Then** 每条能力都有适用场景与证据来源。
2. **Given** 局限表，**When** 阅读，**Then** 每条局限都有规避方式。
3. **Given** 一个具体诉求，**When** 用判据评估，**Then** 能给出「交给 DSH / 留在人工 / 另建服务」的结论。

### User Story 4 - 两条使用路线：工作台与外部系统接入（Priority: P1）

读者能区分两种用法：把 DSH 当**专项工作台**做长周期交付；以及像日历、HA 这类能力**不必固定死在 DSH 上**。
当集群暂时没有其他 agent 时，读者知道这些能力的**上下文与记忆该放在哪**、过渡期怎么做。

**Why this priority**: 这是用户提出的真实取舍，也是本方向最容易写空的地方。

**Independent Test**: 用决策表回答三个具体问题：日历接入放哪、HA 上下文放哪、过渡期由谁承载。

**Acceptance Scenarios**:

1. **Given** 工作台路线，**When** 阅读，**Then** 能看到长会话交付的工作方式、边界与退出条件。
2. **Given** 外部接入路线，**When** 阅读，**Then** 能看到「为什么不硬塞进 DSH」的理由与替代架构。
3. **Given** 集群暂无其他 agent，**When** 阅读过渡方案，**Then** 能说出上下文与记忆的临时归属与后续迁移路径。

### User Story 5 - 落地：vibe coding 与自维护 k3s 集群（Priority: P2）

读者能看到 agent 在写代码与维护集群两类场景下的具体用法：可复用工作流、人的分工、现有组件能做什么、
未接入的开源项目如何登记与后续接入。

**Why this priority**: 落地场景决定这套内容有没有用。

**Independent Test**: 挑一个集群里已有的组件（如配置中心或任务服务），按页面工作流走一遍，能说出 agent 负责什么、人负责什么。

**Acceptance Scenarios**:

1. **Given** vibe coding 工作流，**When** 阅读，**Then** 能看到需求、计划、实现、验证、提交五步与人的把关点。
2. **Given** 集群现状，**When** 阅读实践清单，**Then** 每条实践都对应一个已有组件。
3. **Given** 未接入的开源项目，**When** 查看登记，**Then** 只出现目录与「待补」标注，不出现空页面。

### User Story 6 - 每个服务一个入口：地址、权限与复用（Priority: P2）

读者能看到「服务多了以后」的入口架构：每个服务一个独立入口，入口有自己的地址与权限；
入口组件只写一次、各服务复用；新增服务按声明式步骤接入。读者能分清 DSH 与入口各自干什么。

**Why this priority**: 用户明确指出 DSH 只是开发台入口，日历这类服务需要自己的运行时入口；
服务一多，没有统一入口规范就会变成一堆散落页面与失控的权限。

**Independent Test**: 用日历、HA、任务服务三个服务画出入口表（地址、角色、权限、凭据与记忆归属），
并说明同一诉求什么时候进 DSH、什么时候进服务入口。

**Acceptance Scenarios**:

1. **Given** 三个服务，**When** 看入口表，**Then** 每个服务一行，含地址、可见角色、可操作角色、凭据归属。
2. **Given** 三类角色（只读、操作、管理），**When** 越权请求，**Then** 被拒并留下审计记录。
3. **Given** 新增第四个服务，**When** 按接入步骤操作，**Then** 不超过五步且不需要改入口组件代码。
4. **Given** 同一诉求，**When** 用分工判据评估，**Then** 能判断该进开发台还是进服务入口。

### User Story 7 - 按既有方向的格式成文，且可直接公开发布（Priority: P1）

读者在站点上看到的新方向，与既有方向（如 Python 后端）在元数据、目录层级、讲的组织与用语上完全同构；
同时内容不含任何只能出现在内网的信息，可以直接随本仓同步到公网。

**Why this priority**: 本仓会同步到 GitHub。格式不同构会让新方向成为孤岛，信息不脱敏则会直接泄漏。

**Independent Test**: 对照既有方向抽查 3 讲（元数据字段、四段式与教学要素、官方依据、导航层级），
再对新增页面跑一次泄漏扫描，两处都应无差异、无命中。

**Acceptance Scenarios**:

1. **Given** 新领域目录，**When** 与既有方向对比，**Then** 元数据字段与目录层级一致，导航自动出现该领域。
2. **Given** 任一新增讲，**When** 阅读，**Then** 四段式、教学要素、官方依据与面试追问链齐备。
3. **Given** 全部新增页面，**When** 跑泄漏扫描，**Then** 内网域名、私有地址、内网路径与凭据模式 0 命中。
4. **Given** 公网站点，**When** 浏览新方向，**Then** 页面与图解均可访问，无内网链接、无 404。

### Edge Cases

- 未接入的开源项目（opendesign 等）：只登记，不建空页。
- DSH 能力无法在本地复现的情形：必须写明「依据来源」而不是断言。
- 外部系统涉及鉴权与凭据：必须写明凭据归属，不把密钥写进文档。
- 记忆带来的隐私与清理：必须给出保留期与删除路径的建议。
- 多 agent 的成本失控与死循环：必须给出上限与熔断做法。
- 并发下的资源争用：必须给出限额、排队与背压的判定。
- 读者的前置差异：读者可能只会用聊天工具，需给出最小前置说明。
- 服务数量增长后的入口爆炸：必须有统一入口组件与地址规范。
- 同一服务的入口与开发台同时操作：必须说明冲突检测与以谁为准。
- 凭据轮换与最小权限：必须说明轮换期间入口如何不中断。
- 审计记录本身含敏感信息：必须说明脱敏与保留期。
- 调研热度数据会过期：必须标注核实日期，并说明复核周期。
- 候选项目许可证不兼容或已停更：必须给出替代候选与不采纳理由。
- 检索受限时：改用原生 HTTP 取公开数据；仍取不到则标「待核实」，不得用记忆中的数字充当事实。
- 内部信息边界：哪些经验可以写、哪些只能抽象成能力类别，必须逐条给出判据，避免「以为脱敏其实可定位」。
- 公开仓不能引用内网链接：正文里的链接必须全部指向公开可访问的地址。
- 读者可能把泛化描述误读为某组织专属：必须说明表述已抽象化，示例不代表具体组织。

## Requirements *(mandatory)*

### Functional Requirements

**领域结构与主线**

- **FR-001**: 站点 MUST 新增 `agent` 领域，URL 前缀为 `/agent/`，导航与现有领域同构；新增领域 MUST NOT 修改站点配置。
- **FR-002**: 领域首页 MUST 给出学习路径，主线阶段 MUST ≥5 且按先后排列。
- **FR-003**: 每个阶段页 MUST 写明：解决了什么、带来了什么新问题、代表能力、局限，并给面试追问链。
- **FR-004**: 术语 MUST 统一并给术语表（至少含 agent、工具、上下文、记忆、协同、并发、工作台、接入）。
- **FR-005**: 本方向内容 MUST 遵守四段式与既有教学要素要求。

**原理与实现**

- **FR-006**: 「agent 定义」MUST 给出可判别判据，MUST 与「带工具的聊天」区分开。
- **FR-007**: 最小 agent MUST 用示例讲清循环、工具调用、终止条件与失败处理；示例可为可运行片段或伪代码，本仓 MUST NOT 为此新增项目代码。
- **FR-008**: 协同 MUST 讲清至少三类拓扑（主从、对等、流水线），每类给适用场景与失败模式。
- **FR-009**: 并发 MUST 讲清至少三类模型（进程、线程、异步），并给隔离、限额、取消与背压的做法。
- **FR-010**: 页面 MUST 给出「该用/不该用 agent」的判断清单。

**平台**

- **FR-011**: DSH 能力表 MUST ≥8 条，每条含适用场景与证据来源。
- **FR-012**: DSH 局限表 MUST ≥6 条，每条含规避方式。
- **FR-013**: MUST 给出两条使用路线的选择判据：专项工作台、外部系统接入。

**归属与过渡**

- **FR-014**: MUST 给出上下文与记忆的归属决策表（至少三类：放平台、放外部服务、留在人工），并说明理由。
- **FR-015**: 集群暂无其他 agent 时，MUST 给出过渡方案与后续迁移路径。
- **FR-016**: 外部系统接入 MUST 写明凭据归属与最小权限原则。

**落地**

- **FR-017**: vibe coding MUST 给可复用工作流（需求、计划、实现、验证、提交）与人的把关点。
- **FR-018**: 自建集群的实践 MUST 以抽象能力类别给清单（例如配置管理、任务调度、文档交付、权限入口），MUST NOT 写具体产品、版本、拓扑、地址或节点信息。
- **FR-019**: 未接入的开源项目 MUST 以 `outline` 知识域登记，MUST NOT 建空页面。
- **FR-020**: 每讲 MUST 给官方依据与版本差异（≥2 条官方链接）。
- **FR-021**: 内容涉及组件落地时，MUST 只给设计规范、复用建议与验收口径；本仓 MUST NOT 实现组件代码，MUST NOT 新增复用清单条目。
- **FR-022**: 示例与图解 MUST 自包含；调研引用以文本链接给出，页面 MUST NOT 依赖外部资源加载；MUST NOT 引入第三方运行时依赖。
- **FR-023**: 本方向 MUST 与既有领域互链（如云原生、后端组件页）。
- **FR-024**: 范围边界 MUST 写明：本专题只交付调研、架构与规范；真实日历/HA 等服务的接入、部署与代码改动都不在本专题；
  不写未公开的平台内部实现，不承诺未验证能力。

**多服务入口**

- **FR-025**: 每个服务 MUST 有独立入口地址，MUST NOT 与其他服务共用同一路径。
- **FR-026**: 入口 MUST 按角色区分权限，至少覆盖只读、操作与管理三类。
- **FR-027**: 一次入口会话 MUST 只绑定一个服务，MUST NOT 跨服务复用会话。
- **FR-028**: 每次控制操作 MUST 留审计记录：谁、何时、对哪个服务、做了什么、结果如何。
- **FR-029**: 新增服务接入 MUST 走声明式步骤（服务名、地址、权限、记忆归属），MUST NOT 改入口组件代码。
- **FR-030**: 入口方案 MUST 给出可复用的设计规范（地址规范、权限模型、记忆归属、接入步骤），并调研业界现成的入口与网关方案；MUST NOT 在本仓实现组件。
- **FR-031**: 凭据 MUST 由服务侧或独立密钥管理提供，MUST NOT 写进入口页面或记忆。
- **FR-032**: 记忆归属 MUST 分三层：入口会话记忆（短期）、服务记忆（长期，归服务）、平台记忆（跨服务，按授权可见）。
- **FR-033**: 入口 MUST 有限流与熔断，MUST NOT 让单个使用者压垮后端服务。
- **FR-034**: 文档 MUST 写明开发台与入口的分工判据：长周期专项交付进开发台，运行时按服务控制进入口。

**业界调研与选型**

- **FR-035**: 每个主题 MUST 先调研业界常用开源项目（GitHub 热门或生产在用），MUST NOT 只讲自研思路。
- **FR-036**: 每个候选 MUST 给出：名称、仓库或官方文档链接、许可证、维护活跃度、适用场景与主要代价。
- **FR-037**: 热度与活跃度数据 MUST 标注**核实日期与来源**；MUST NOT 出现无来源的星标或下载量数字。
- **FR-038**: 每个主题 MUST 给对比表与「采纳／参考／不采纳」结论；不采纳的 MUST 写清理由。
- **FR-039**: 调研 MUST 覆盖至少四类：agent 框架与运行时、多服务入口与网关、身份与权限、上下文与记忆。
- **FR-040**: 调研 MUST 落到本集群现状，逐项回答：现有组件已能覆盖什么、还缺什么、缺的用开源还是自建。
- **FR-041**: 本仓 MUST NOT 修改被调研项目的代码，MUST NOT 在本仓实现这些服务；只产出文档与设计建议。
- **FR-042**: 每个主题 MUST 给可行性判断：能做什么、不建议做什么、代价与风险各是什么。
- **FR-043**: 引用 MUST 可核验（仓库、官方文档或发布说明），并标注版本或访问日期。

**公网发布安全**

- **FR-044**: 内容 MUST 可公开发布：MUST NOT 出现内网域名、私有地址、主机名、内网端口或内网仓库路径。
- **FR-045**: 涉及自建集群的经验 MUST 用抽象能力类别表述（例如「配置中心」「任务服务」「文档站」），MUST NOT 写具体产品版本、部署拓扑、节点数量或集群规模。
- **FR-046**: MUST NOT 出现任何凭据、令牌、密钥、内部账号、内部工单号或内部链接。
- **FR-047**: 调研 MUST 只使用公开来源（代码托管平台接口、官方文档、发布说明），MUST NOT 引用内部系统数据或截图。
- **FR-048**: 发布前 MUST 对新增页面跑泄漏扫描：内网域名、私有地址、内网路径与凭据模式命中即失败。
- **FR-049**: 需要背景铺垫时 MUST 用泛化表述（例如「一套自建集群」「某个团队」），MUST NOT 暴露可定位到具体组织的信息。

**与既有方向同构**

- **FR-050**: 目录与元数据 MUST 与既有方向一致：领域元数据含名称、图标、顺序、描述与入口类型，且新增领域 MUST NOT 需要改站点配置。
- **FR-051**: 组织层级 MUST 沿用既有分层（领域 → 知识域 → 讲），导航层级 MUST 可达三级（`1.1.1`）。
- **FR-052**: 每讲 MUST 齐四段式与既有教学要素，并给面试追问链。
- **FR-053**: 每讲 MUST 给官方依据与版本差异（≥2 条官方链接，标注适用版本）。
- **FR-054**: 用语 MUST 与既有方向的术语风格一致；新增术语 MUST 进术语表。

### Key Entities

- **Domain**：新领域 `agent`；名称、图标、顺序、入口类型与学习路径。
- **EvolutionStage**：演进阶段；名称、解决了什么、新问题、代表能力、局限。
- **AgentLoop**：最小 agent 的循环；观察、决策、行动、终止与失败处理。
- **CollaborationTopology**：协同拓扑；主从、对等、流水线；适用与失败模式。
- **ConcurrencyModel**：并发模型；进程、线程、异步；隔离、限额、取消、背压。
- **CapabilityEntry**：平台能力或局限；名称、场景、证据来源、规避方式。
- **ContextOwnership**：上下文与记忆归属；对象、存放位置、理由、迁移路径。
- **PracticeItem**：落地实践；场景、对应组件、agent 职责、人的职责。

- **ServiceEntry**：服务入口；服务名、独立地址、入口组件、绑定权限。
- **AccessPolicy**：访问策略；角色（只读/操作/管理）、可执行动作、拒绝后的审计要求。
- **EntrySession**：入口会话；绑定服务、有效期、短期记忆范围。
- **MemoryLayer**：记忆分层；入口会话记忆、服务记忆、平台记忆及其归属与保留期。
- **AuditRecord**：审计记录；操作者、时间、服务、动作、结果。

## Assumptions

- 新领域顺序排在现有三个领域之后（order 取 4），图标与命名遵循既有风格。
- 「DSH」指本会话使用的 DeepSeek Harness；能力与局限以本仓可复现或可验证的行为为据，不引用未公开内部实现。
- 日历、HA 等外部系统本专题只给架构、权限与归属方案，不实现真实集成；真实接入留待后续专题。
- DSH 是开发台入口；每个服务另有运行时入口。本仓只给入口的设计规范与业界对比，不实现组件。
- 本仓定位为文档与可行性研究：不修改项目代码、不部署服务，产出只有 Markdown 与自包含图解。
- 调研优先级：GitHub 热门、业界常用、有生产案例的项目优先；候选清单与热度数据须在实现阶段联网核实并标注来源与日期。
- 原生 HTTP 取数已实测可用：2026-10-18 用公开接口取到多个候选项目的星标数、许可证与最近提交时间；
  调研以此为准，并逐条标注抓取日期。
- 本仓内容默认公开（同步到代码托管平台的 Pages）；任何页面按公开发布标准写。
- 既有方向（如 Python 后端）是格式基准：元数据、目录层级、讲的组织与用语都向它对齐。
- opendesign 等尚未接入的开源项目先登记为 `outline`，等内容开写再扩。
- 示例优先使用 Python 标准库，与既有并发域保持一致。
- 本方向读者画像包含「会用聊天工具但不了解 agent」的人，需要最小前置说明。
