# Phase 0 研究：GitHub Actions 双远端发布与 GitHub Pages 站点

侦察事实（本地实测）：

| 事实 | 值 | 影响 |
|---|---|---|
| 仓库内流水线 | 只有 `.gitea/workflows/ci.yaml`，**无 `.github/`** | 需新增 GitHub 侧流水线 |
| 站点配置 | `cleanUrls: true`，**无 `base`** | 子路径与深链是主要风险 |
| 产物形态 | `docs/.vitepress/dist/backend/…/thread-basics.html`（无扩展名链接） | 深链需兜底 |
| 组件动态链接 | 7 个组件、**15 处 `:href`**，值来自引擎的 `/domain/...` | 子路径下会指错 |
| markdown 绝对链接 | **119 处** `](/...)` | 由站点框架自动加基础路径前缀 |
| 图解资源 | 11 张，合计约 8.1MB，自包含 | 在托管限制内，无需外链 |
| GitHub 仓库可见性 | 匿名访问返回 200 → 公开可读 | Pages 在免费计划可用 |

## D1 基础路径如何进入构建

- **决策**：`docs/.vitepress/config.mts` 读环境变量（如 `DOCS1_BASE`），默认 `/`；
  内网构建不设该变量（保持根路径），Pages 构建设为 `/docs1/`。
- **理由**：同一份内容与引擎服务两个目标，避免复制内容或维护第二套配置（原则 I）。
- **备选**：写死 `base: '/docs1/'`（内网根路径失效）；用相对基础路径（框架不支持，绝对资源仍会失效）。

## D2 组件内链接如何适配子路径

- **决策**：主题内 7 个组件的 15 处动态链接统一改用框架提供的基础路径前缀函数
  （如 `withBase()`），值仍来自引擎，只在渲染时加前缀。
- **理由**：框架只自动处理 markdown 链接，动态绑定的 href 不受保护；
  两套组件行为比一处适配更容易出错。
- **备选**：在引擎里直接产出带前缀的 URL（会污染内容模型与门禁判据，linkMap 与锚点都会受影响）。

## D3 深链与平台行为

- **决策**：发布产物必须包含 **`.nojekyll`** 与一个**深链兜底页**（`404.html`）：
  兜底页按「先试 `<path>.html`，再试 `<path>/index.html`，最后回首页」的顺序处理，
  并保留查询串与锚点。
- **理由**：产物是无扩展名链接，平台对深链的解析不在我们控制内；
  用确定性兜底替代对平台行为的赌博。兜底页同时覆盖从外部直接粘链接进入的场景。
- **备选**：为 Pages 单独构建 `cleanUrls: false`（链接带 `.html`，与内网观感不一致，且需第二套构建口径）；
  仅依赖平台解析（一次差异即全站深链 404）。

## D4 发布动作与权限

- **决策**：使用平台官方发布动作三件套（配置 Pages → 上传产物 → 部署），
  工作流声明 `contents: read`、`pages: write`、`id-token: write`，并绑定 `github-pages` 环境；
  配置步骤启用「自动开启 Pages」能力（`enablement: true`）。
- **理由**：官方动作是 Pages 发布的支持路径；显式权限最小化；环境绑定让发布记录可追溯。
- **备选**：推送到 `gh-pages` 分支（需额外分支与令牌管理，且与「Settings → Pages」配置耦合更紧）。

## D5 门禁在托管侧同源

- **决策**：GitHub 侧执行与内网侧**同一套十一条门禁**，并新增一条产物门禁；
  托管 runner 需自备 Python 与测试框架（公共源安装）。
- **理由**：公网内容不得比内网宽松（原则 III/IV）；门禁失败即不发布（FR-006）。
- **备选**：托管侧只构建不校验（内容退化无人拦）。

## D6 并发与「最新提交」语义

- **决策**：流水线使用按分支分组的并发组并开启取消进行中的旧运行，保证最终发布对应最新提交。
- **理由**：连续推送时旧运行可能后完成并覆盖新产物（FR-013）。
- **备选**：不做并发控制（发布回退风险）。

## D7 降级行为与内网地址零泄漏

- **决策**：公网静态产物不得包含内网域名或私有地址；依赖后端的组件在静态托管下显示降级提示，
  文案说明「服务不可用」与影响范围；新增产物门禁做两件事：
  ① 断言产物中不出现内网地址清单中的字符串；② 断言基础路径前缀在产物链接中正确。
- **理由**：公网暴露内网信息是安全问题；降级提示已在组件内实现，需要门禁固化。
- **备选**：人工抽查（漏一次即长期暴露）。

## D8 内网链路保持不变

- **决策**：Gitea 工作流、Caddy 配置、K8s 清单与镜像标签规则**不改**；
  只在站点配置层增加「基础路径可注入」这一处改动，默认值与现状一致。
- **理由**：已有链路可用且被多次验收（FR-011）。
- **备选**：把两套发布合并成一条流水线（强耦合，一侧故障会拖住另一侧，违反 FR-005）。

## 结论

八个决策均可在不引入内网依赖、不改动内网交付物的前提下落地；
最大的两处风险（子路径链接、深链解析）分别用「统一前缀适配」与「确定性兜底页」消解，
并有对应的机械门禁与发布后抽查。
