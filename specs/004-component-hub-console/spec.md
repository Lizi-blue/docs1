# Feature Specification: 组件首发仓与前后端双端任务控制台（component-hub-console）

**Feature Branch**: `004-component-hub-console`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: 「前端体验很差，需要专业的前端提高前端 UI 设计与体验。此外我让前后端分别为实现一个完整的 多线程多进程任务控制台组件，实现任务下发调度执行日志实时显示功能。`https://docs1.minilab.uzibird.cn/backend/components/task-console` 怎么在后端的地址中记录的是前端的内容？我需要分别在前后端分别看到实现对应的部分，并且详细索引到依赖的知识域知识点，让我快速学会这部分，并且能快速将组件的代码复用到别的项目中。本项目的主旨是通过不同方向的知识域知识点引导我渐进式学习，结合这些知识点做出一些可复用的组件，让我快速复用到其他生产项目，并且这个仓也要当作一些组件的模板仓或组件仓，我在其他生产项目开发时也会先保证这个仓拥有对应的组件，会先在这个仓开发组件，将此写入宪法。」（承宪法 1.4.0 原则 VI 组件按生产级交付与原则 X 导航层级与接口覆盖）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 双端各看到自己那一份实现（Priority: P1）

读者分别进入后端与前端组件区，各自只看到与本方向相关的实现：后端看到任务调度、进程与线程管理、取消与监控；前端看到提交、状态呈现与实时日志面板。两个页面互相链接，可以对照阅读，也可以只取自己需要的一份。

**Why this priority**: 当前后端地址下记录的是前端内容，方向错配直接破坏「按方向渐进学习」的主旨。

**Independent Test**: 分别打开后端与前端组件页，断言两页正文与依赖清单不含对方方向内容，且两页相互链接可达。

**Acceptance Scenarios**:

1. **Given** 读者从领域导航进入后端组件区，**When** 打开任务控制台组件页，**Then** 页面只讲后端实现（调度、并发、进程组、取消、监控），并给出去前端对应页的链接。
2. **Given** 读者进入前端组件区，**When** 打开任务控制台组件页，**Then** 页面只讲前端实现（交互、状态呈现、实时日志、错误与降级），并给出去后端对应页的链接。
3. **Given** 任一页面，**When** 抽检正文与依赖清单，**Then** 0 处方向错配。

### User Story 2 - 依赖的知识点可点可学（Priority: P1）

每个组件页把依赖的知识域与知识点列成索引：每条给出页面链接，以及「这个知识点在组件里承担什么」。读者顺着索引就能把组件用到的知识补齐。

**Why this priority**: 组件是知识点的组合结果；没有细粒度索引，读者只能猜需要先学什么。

**Independent Test**: 从组件页出发点击每条依赖，断言全部落到真实页面，且每条都写明在组件中的作用。

**Acceptance Scenarios**:

1. **Given** 组件页的「依赖的知识点」索引，**When** 逐条点击，**Then** 每条都打开对应知识点页（无 404）。
2. **Given** 索引中的任一条，**When** 阅读该条说明，**Then** 能看懂该知识点在本组件中解决什么问题。
3. **Given** 读者想按知识域筛选组件，**When** 打开组件索引页，**Then** 可按方向与依赖知识域缩小范围。

### User Story 3 - 复制即可复用（Priority: P1）

读者把组件搬进自己的生产项目：页面给出最小文件清单、外部依赖、需要改的适配点与接口契约，照着做就能跑起来。

**Why this priority**: 本仓定位为组件首发仓与模板仓，复用成本决定它是否真的被用起来。

**Independent Test**: 按页面给出的骨架在空项目里落地该组件，断言能跑通既定功能。

**Acceptance Scenarios**:

1. **Given** 组件页的复用章节，**When** 读者按清单复制文件并安装依赖，**Then** 组件在不依赖本仓其余部分的情况下可运行。
2. **Given** 读者的项目接口地址与示例不同，**When** 按页面标出的适配点修改，**Then** 组件仍能完成提交与实时日志显示。
3. **Given** 组件页，**When** 读者查看契约章节，**Then** 能看到组件要求外部提供的接口与事件约定。

### User Story 4 - 专业的前端体验（Priority: P2）

站点与可复用前端组件都遵循统一设计规范：排版、色彩、间距、圆角与阴影有令牌；交互元素具备默认、悬停、焦点、禁用与加载状态；空态、错误态与降级态都有明确呈现；键盘可完成主要操作；移动端与桌面端都不横向溢出；深色模式可用。

**Why this priority**: 读者长时间停留在这个站点，观感与操作流畅度直接影响学习意愿。

**Independent Test**: 按设计规范逐项抽检站点与组件，断言状态齐全、键盘可操作、无横向溢出。

**Acceptance Scenarios**:

1. **Given** 任一带交互的界面，**When** 用键盘 Tab 与回车操作，**Then** 可完成提交与取消。
2. **Given** 窄屏设备，**When** 打开知识点页与组件页，**Then** 正文不横向溢出，宽内容在自身容器内滚动。
3. **Given** 服务不可用，**When** 打开控制台组件，**Then** 出现明确的降级提示而不是空白。
4. **Given** 深色模式，**When** 切换主题，**Then** 组件与站点观感一致且对比度可读。

### User Story 5 - 本仓是组件首发地（Priority: P1）

读者（也是维护者）在别处开发生产项目时，先回到本仓把需要的组件做出来、写清契约与复用步骤，再复制到那个项目；本仓因此持续积累可复用组件与模板。

**Why this priority**: 这是用户明确的长期工作方式，必须写成规则才有约束力。

**Independent Test**: 核查宪法含该条款，且组件页具备「契约 + 骨架 + 依赖索引」三件套。

**Acceptance Scenarios**:

1. **Given** 宪法，**When** 阅读组件相关原则，**Then** 明确要求组件 MUST 先在本仓成型再复制到其他项目。
2. **Given** 一个新增组件，**When** 提交评审，**Then** 缺契约、骨架或依赖索引即不通过。

### Edge Cases

- 同一功能的两端由不同人维护：页面归属与交叉链接如何保持一致。
- 组件依赖的知识点尚未开写（outline）：索引需要指向「待补」而不是死链。
- 组件被复制到使用不同鉴权或不同接口路径的项目：适配点必须显式列出。
- 前端在无服务环境下：必须呈现降级态，不能白屏或抛未捕获错误。
- 站点样式改动与组件样式互相污染：组件样式需限定作用域。
- 深色模式与移动端同时生效时的可读性。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 本仓 MUST 被定义为组件首发仓与模板仓：组件 MUST 先在本仓成型（含文档、接口契约、可复用骨架与验收方式），再复制到其他生产项目。
- **FR-002**: 后端组件页 MUST 只描述后端实现，前端组件页 MUST 只描述前端实现；同一功能的两端页面 MUST 互相链接。
- **FR-003**: 每个组件页 MUST 给出依赖的知识域与知识点索引，每条 MUST 含页面链接与该知识点在本组件中的作用说明。
- **FR-004**: 依赖索引中的链接 MUST 全部有效；指向尚未开写的知识域时 MUST 标为「待补」而不是死链。
- **FR-005**: 每个组件页 MUST 提供复用四件套：接口契约（见 FR-006）、最小骨架（含最小文件清单、外部依赖与需要修改的适配点）、依赖知识索引（见 FR-003）与可复现的验收步骤。
- **FR-006**: 每个组件页 MUST 给出对外接口契约：需要外部提供的接口、事件或数据形态，以及失败与降级约定。
- **FR-007**: 组件 MUST 能在不依赖本仓其余部分的情况下独立运行，并有可复现的验收步骤。
- **FR-008**: 站点 MUST 同时提供后端组件区与前端组件区，导航可分别到达。
- **FR-009**: 组件索引页 MUST 支持按方向（后端/前端）与依赖知识域筛选。
- **FR-010**: 站点与可复用前端组件 MUST 遵循统一视觉规范：色彩、字号、间距、圆角、阴影以设计令牌表达，MUST NOT 在页面里散落魔法值。
- **FR-011**: 交互元素 MUST 具备默认、悬停、焦点、禁用与加载状态；MUST 提供键盘可达的焦点样式。
- **FR-012**: 界面 MUST 覆盖空态、错误态与降级态；错误提示 MUST 说明原因与下一步动作。
- **FR-013**: 主要操作 MUST 可用键盘完成（含提交与取消）。
- **FR-014**: 站点与组件 MUST 在手机、平板与桌面三档均不出现横向溢出；宽内容 MUST 在自身容器内滚动。
- **FR-015**: 深色模式 MUST 可用，且前景与背景对比满足可读性要求。
- **FR-016**: 组件样式 MUST 限定作用域，MUST NOT 污染站点其他页面。
- **FR-017**: 宪法 MUST 新增或扩写一条原则，写明「本仓为组件首发地与模板仓」及其约束。
- **FR-018**: 既有内容契约 MUST 继续满足：组件页必需章节、官方依据与版本差异、API 方法组分层与条目字段要求。

### Key Entities

- **Component**：方向（后端/前端）、名称、依赖知识域与知识点、接口契约、复用四件套、验收方式。
- **KnowledgeDependency**：知识点页面引用、在本组件中的作用说明、是否待补。
- **DesignToken**：色彩、字号、间距、圆角、阴影与状态样式。
- **ReuseKit**：复用四件套的载体——接口契约、最小骨架（文件清单、外部依赖、适配点）、依赖知识索引、可复现的验收步骤。
- **DirectionIndex**：后端组件区与前端组件区各自的索引与筛选条件。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从任一组件页出发，最多两次点击即可到达它依赖的每个知识点页面。
- **SC-002**: 抽检全部组件页，方向错配 0 处（后端页不含前端实现正文，前端页不含后端实现正文）。
- **SC-003**: 按组件页给出的骨架，在空项目中 10 分钟内可跑通该组件的基本功能。
- **SC-004**: 组件页依赖索引链接有效率 100%（含「待补」标注），机械校验可复现。
- **SC-005**: 交互逐项检查通过：默认、悬停、焦点、禁用、加载、空态、错误态、降级态各有明确呈现。
- **SC-006**: 键盘可完成提交与取消；焦点可见。
- **SC-007**: 三档视口下横向溢出为 0；深色模式下正文对比可读。
- **SC-008**: 宪法含组件首发仓条款，且既有门禁与自检全部保持通过。

## Assumptions

- 使用者为内网单人维护者，站点无鉴权；组件默认面向内网环境。
- 前端以 Vue 3 单文件组件为主，后端以 Python 标准库服务为主；两者通过同源 HTTP 与事件流协作。
- 设计规范自建（设计令牌 + 少量基础样式），不引入第三方 UI 组件库，避免依赖与离线构建风险。
- 「专业的前端」以本仓自建设计规范与可机械校验的体验项衡量，不引入外部设计评审流程。
- 组件按需增长：先覆盖任务控制台两端，其余组件沿用同一模板与门禁，逐步补齐。
- 组件契约的版本变化不破坏已复制到其他项目的用法：破坏性变更 MUST 在页面标注迁移步骤。
