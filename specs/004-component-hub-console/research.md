# Phase 0 研究：组件首发仓与前后端双端任务控制台（decision / rationale / alternatives）

规格 18 条功能需求无 NEEDS CLARIFICATION，但有七个设计决策会显著影响实现与验收，
逐条记录选择与取舍。判据以宪法 1.5.0 原则 I、VI、XI 为准。

## D1 方向（后端/前端）如何标注

- **决策**：组件页 frontmatter 新增必填字段 `direction: backend | frontend | fullstack`；
  门禁校验 `direction` 与所在领域的映射（`backend/*` 只允许 `backend`；`frontend/*` 只允许 `frontend`；
  `cross-domain/*` 只允许 `fullstack`），并扫描正文的方向标记词。
- **理由**：修复「后端地址下记着前端内容」只能靠显式元数据加机械判据；
  目录本身只表达领域，不表达方向（云原生领域天然跨端）。
- **备选**：仅靠目录约定（无法表达 fullstack，且历史上已错过一次）；仅靠人工评审（无回归能力）。

## D2 复用清单放在哪里

- **决策**：新增 `reuse/<component>/manifest.json` 作为复用四件套的唯一事实源
  （文件清单、外部依赖、适配点、验收命令、契约版本、对应页面），组件页渲染它。
- **理由**：原则 I 要求单一事实源。清单必须能被门禁校验「与实际文件一致」，
  页面代码块做不到这一点；复制时也容易漏文件。
- **备选**：只写页面（无法机械校验、易漂移）；把清单写进 frontmatter（页面渲染简单，
  但大量文件路径与命令塞进页面头部，可读性差且不利于被其他组件复用同一模板）。

## D3 前端设计体系：自建令牌还是引入 UI 库

- **决策**：自建设计令牌层 `docs/.vitepress/theme/styles/tokens.css`，
  在 VitePress `--vp-*` 变量之上派生间距阶梯、字号、圆角、阴影、状态色与焦点环；
  组件与站点样式只引用令牌。不引入第三方 UI 组件库。
- **理由**：本仓离线可构建、依赖私有索引，第三方库会带来构建与体积风险；
  现状 `TaskConsole.vue` 的原始色值计数为 0，说明自建路线成本可控；
  令牌化后「专业前端」才有客观判据（见 D4）。
- **备选**：引入 Element Plus 等库（观感达标快，但引入依赖、破坏零依赖约束、需额外主题适配）；
  只改样式不建令牌（无法机械验收，改动会退化）。

## D4 「专业前端体验」哪些能机械化，哪些不能

- **决策**：拆两处。
  **入 CI 的静态断言**（`scripts/check-experience.mjs`）：令牌文件存在且分类齐全；
  `focus-visible` 规则存在；交互状态类（hover/active/disabled/loading/empty/error）齐备；
  组件样式不含原始色值与魔法尺寸；关键前景背景对按 WCAG 对比度公式算 ≥ 4.5；
  深色模式覆盖同一批令牌；宽内容在窄屏自滚动规则存在。
  **人工清单**（写入 quickstart）：真实键盘 Tab 流程、真实视口观感、屏幕阅读器朗读顺序。
- **理由**：沙箱无浏览器（Playwright 缺系统库、apt 被拒），
  但绝大多数体验约束可以在 CSS/源码层机械判定；把不可判定的部分显式列为人工项，
  避免「无法自动验证」变成「无人验证」。
- **备选**：全部人工（体验会随改动退化）；引入无头浏览器（当前环境不可行，且与原则 VII 冲突）。

## D5 知识依赖索引怎么渲染

- **决策**：组件页 frontmatter 用结构化列表承载依赖：
  `knowledge_index: [{ page: /…/thread-basics, role: "讲清线程生命周期与 join 语义" }]`；
  主题新增 `KnowledgeIndex.vue` 从该字段渲染表格；`depends_on_knowledge` 保留并由脚本从
  `knowledge_index` 派生或校验一致，避免两份清单。
- **理由**：既要「详细索引到知识点」，又要单源。组件渲染消除手写漂移，
  门禁可校验链接有效、`role` 非空、待补知识域被标「待补」。
- **备选**：正文手写表格（与 frontmatter 重复，改一处漏一处）；
  只给链接不给作用（不满足 FR-003 的「承担什么」）。

## D6 组件索引的方向与知识域筛选怎么做

- **决策**：客户端筛选。组件索引页（`EntryIndex kind="components"`）从文档树读取每个组件的
  `direction` 与依赖知识域，渲染方向切换与知识域下拉，筛选在浏览器内完成。
- **理由**：组件数量在个位数到几十，无需额外构建步骤与索引文件；
  文档树已在页面注入，数据现成。门禁只断言筛选控件存在与依赖字段完整。
- **备选**：构建期生成多份静态索引页（组件多了才有价值，当前属过度设计）。

## D7 后端组件与既有任务服务的关系

- **决策**：后端组件页直接以 003 落地的 `service/` 为实体（调度、进程组、取消、监控、SSE），
  页面与其 `reuse` 清单绑定；**不重写、不复制**第二份实现。
  组件页只讲后端实现，前端组件页只讲前端实现，两端通过链接互相指路。
- **理由**：原则 I 与 XI 都要求单源；003 的服务已上线且有用例覆盖（46 passed），
  重写会立刻产生两份漂移实现。
- **备选**：为「组件模板仓」另写一份精简服务（产生第二份实现与维护负担）。

## D8 破坏性变更与迁移（规格 Assumptions 末条）

- **决策**：`reuse/task-console/manifest.json` 增加 `contractVersion`；
  组件页渲染契约版本与迁移步骤小节；变更契约时版本号递增并在页面写迁移说明。
- **理由**：组件会被复制到其他项目，契约漂移必须可追溯（原则 XI 最后两条）。
- **备选**：无版本（复制出去的项目无从判断兼容性）。

## 结论

七个决策均可在不引入新依赖、不新增端口与数据库的前提下落地；
所有门禁为 Node 静态断言与既有 pytest，符合原则 VII。
