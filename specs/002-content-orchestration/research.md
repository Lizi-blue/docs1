# Phase 0 Research: 内容编排与教学法技能（002-content-orchestration）

格式：**决策 / 理由 / 备选方案 / 落地状态**。全部结论均可机械核对，不依赖人工印象。

## R1 技能落位与忽略规则收窄

**决策**：技能放在 `.dsh/skills/docs-authoring/`（宪法 VIII 指定）。`.gitignore` 的 `.dsh/`
收窄为 `.dsh/skills/speckit-*`，使本技能可入库，同时继续忽略 spec-kit 生成的同名技能副本。

**理由**：宪法 VIII 已把仓内技能位置写死；忽略规则原本是为排除 spec-kit 的重复副本，
用通配整目录会误伤自研技能。

**备选方案**：放到 `docs/` 之外的新目录（与宪法冲突，需改宪法）；把技能提交进 `dev/skill`
而不在仓内保留（违反 FR-001「仓内可直接加载」）。

**落地状态**：待实现（计划的首个前置任务）。

## R2 技能正文结构

**决策**：`SKILL.md` 固定九节，顺序不可变：

1. 何时加载；2. 目录落位与命名；3. 编排判据（知识点拆分与合并、知识域划分、路径排法与长度、
   组件与知识点对应）；4. 每讲教学结构（四要素）；5. 模板（`teach` 块、知识点骨架、组件骨架、
   路径声明）；6. 工具选用（写作规则、交互图解含图型表、云架构静态图，各配反例）；
7. 常见错误与修法；8. 自检与门禁命令；9. 优先级声明（宪法 > 内容契约 > 技能）与变更日志指针。

**理由**：固定节序让自检可断言「章节齐全」；也让人和 Agent 都能按同一路径找到判据。

**备选方案**：自由结构（无法机械检查）；按主题拆多文件（跨仓导出与加载复杂度上升）。

**落地状态**：待实现。

## R3 教学要素的落位

**决策**：每讲四个要素固定在以下位置，标题逐字如下：

| 要素 | 标题 | 位置 |
|---|---|---|
| 本讲要解决的问题 | `### 本讲要解决的问题` | `## TL;DR` 之前 |
| 常见误区 | `### 常见误区` | `### 面试追问链` 之前 |
| 面试追问链 | `### 面试追问链` | 第四段内（已存在） |
| 下一讲衔接 | `### 下一讲衔接` | `### 关联组件` 之前 |

**理由**：不动四段式既有必需小节（001 的 V7 依赖那些 H2 标题）；H3 落在段内，既满足教学节奏，
又不破坏结构校验。

**备选方案**：新增一个 H2「学习引导」承载四要素（会改变四段式契约，波及 001 的校验与 8 个页面）；
把要素塞进 frontmatter（长文本不适合放在元数据里）。

**落地状态**：待实现（8 页收口时同步落位）。

## R4 登记块形态与向后兼容

**决策**：知识域 `_meta.yml` 新增 `teach:` 块：

```yaml
teach:
  audience: "有 Python 基础、准备中高级面试的开发者"
  prerequisites: ["Python 语法与标准库基础"]
  outcomes: ["能解释 GIL 对并发选型的影响", "能按任务类型选择线程、进程或协程"]
  path:
    - from: "01-thread-basics"
      to: "04-async-io"
      label: "从线程到异步"
  lessons:
    - slug: "01-thread-basics"
      goal: "讲清线程创建、同步与 GIL 的关系"
```

引擎读路径时按 `teach.path ?? path` 回退，既有 2 个知识域迁移后删除顶层 `path`。

**理由**：FR-025 要求登记与内容同处；`teach` 块内聚后，路径只有一处。
回退读法让schema 升级不导致构建中断。

**备选方案**：集中式登记文件（离内容远，易漏登记）；技能文档内维护表格（无法机械核对）。

**落地状态**：待实现（含迁移 2 个既有文件）。

## R5 迭代台账格式与「连续三次」判定

**决策**：`ledger/orchestration-decisions.tsv`，制表符分隔，首行表头：

```text
date	iteration	scope	decision	reason	review
2026-10-11	002-content-orchestration	技能上线首轮	writeback	新增技能正文与模板	-
```

- `decision` 取值：`writeback` / `no-writeback`。
- `review` 取值：`-` / `recheck:valid` / `recheck:update`。
- 判定算法：从表尾向前统计连续 `no-writeback`；达到 3 条且其后没有 `recheck:*` 记录时判错，
  要求补一条复核记录。

**理由**：一行一记录、字段固定，脚本解析零歧义；顺序即时间顺序，无需解析日期。

**备选方案**：Markdown 表格（列数一变就解析失败）；YAML 列表（合并冲突更痛）；
只写提交信息（无法审查）。

**落地状态**：待实现。

## R6 校验分工与规则编号

**决策**：

| 归属 | 编号 | 检查内容 |
|---|---|---|
| 内容门禁 `check-content.mjs` | V15 | 知识域 `_meta.yml` 含 `teach` 块且五字段齐全、类型正确 |
| 内容门禁 | V16 | 知识点页含四个教学要素（三个 H3 标题存在；`### 面试追问链` 下 `<details>` 条目 3–5 条） |
| 内容门禁 | V17 | `teach.lessons[].slug` 与实际知识点页双向完整（无幽灵条目、无未登记页面） |
| 内容门禁 | V18 | 教学要素内容非空（每个要素下至少 1 行实质文本，不可是标题占位） |
| 独立自检 `check-orchestration.mjs` | S1 | 技能正文内无取值复制（对照内容契约的字段清单与阈值关键串） |
| 独立自检 | S2 | 技能必需章节齐全且顺序正确 |
| 独立自检 | S3 | 台账格式合法 + 「连续三次无需回写」规则 |
| 独立自检 | S4 | 技能到内容契约的指针可达 |
| 独立自检 | S5 | 导出物存在时，其指纹与当前源一致 |

**理由**：Q1 的决策把「内容是否合规」与「技能自身是否健康」分开。内容项进 fail-closed 门禁，
技能项走可单独运行的报告式自检，避免改技能时把整站构建卡住。

**备选方案**：全部进内容门禁（改技能也会卡构建）；全部走自检（内容缺要素可能被漏掉）。

**落地状态**：待实现（V15–V18 挂到 001 的 T006–T009 产出上，S1–S5 为新脚本）。

## R7 导出与指纹算法

**决策**：

- 源区：`SKILL.md` 内用 `<!-- export:begin -->` 与 `<!-- export:end -->` 圈定导出正文（含九节全部内容）。
- 归一化：统一 LF、去掉每行尾空白、去掉首尾空行、文件末尾补一个换行。
- 指纹：归一化正文的 `sha256`，取前 16 位十六进制，写入导出物头部注释：

```markdown
<!--
exported-from: dev/docs-1
source-path: .dsh/skills/docs-authoring/SKILL.md
source-commit: <40 位 sha>
skill-version: 1.0.0
body-sha256-16: <16 位十六进制>
exported-at: <ISO 时间>
do-not-edit: 本文件由 scripts/export-skill.mjs 生成，手改会被自检判错
-->
```

- 导出物落 `build/skill-export/docs-authoring/SKILL.md`（`build/` 已被忽略），
  复制到 `dev/skill` 仓的 `skills/docs-authoring/SKILL.md`。
- 比对：S5 读导出物头部的指纹，对当前源正文重新计算并比较；不一致即判错。

**理由**：既让其他仓独立可用，又让「两份正文」不可能悄悄漂移；归一化避免换行差异造成假警报。

**备选方案**：手写双份 + 人工比对；只放指针（其他仓无法独立使用，违反 SC-007）；
用子模块引用本仓（跨仓加载体验差，且与本仓私有性冲突）。

**落地状态**：待实现。

## R8 既有内容收口方式

**决策**：一次到位。8 个知识点页各补三个 H3 与实质内容，核对追问链条目落到 3–5 条；
2 个知识域各补 `teach` 块并把顶层 `path` 迁入。收口后 V15–V18 全绿，不保留基线。

**理由**：SC-003 要求缺失数为 0；规模只有 8 页，分批反而留下两套写法。

**备选方案**：分批 + 基线（留下一段时间的双写法，读者会看到两种讲法）；只建清单
（教学效果没有任何改善）。

**落地状态**：待实现。
